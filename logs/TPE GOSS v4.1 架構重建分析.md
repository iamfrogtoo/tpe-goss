### 1.3 舊架構核心問題

| 問題 | 說明 | 影響 |
|------|------|------|
| **資料同步斷層** | Python 後端在伺服器，Next.js 前端在 Vercel，兩者無法直接溝通 | 首頁顯示過期資料 |
| **雙重資料庫** | 伺服器有 `goss_v4.db`，本地有 `goss_v4_server.db` | 資料不一致 |
| **GitHub 推送依賴** | 依靠 `push_to_github.py` 定期推送，有 5-10 分鐘延遲 | 即時性差 |
| **CDN 快取** | jsdelivr 有自己的快取机制 | 無法保證最新 |
| **時刻表繞過 API** | schedule/outbound/map 頁面直接抓 Google Sheets，不走 API | 資料來源混亂 |
| **無錯誤回審** | 沒有機制驗證資料正確性 | 錯誤難以發現 |
| **local DB 過期** | `goss-v4/public/live_data.json` 最後更新 4/5，已 7 天未更新 | 完全過期 |

## 2. 新架構建議

### 2.1 方案 A：全雲端 Serverless 架構（推薦）

**核心理念**：將 Python 後端邏輯迁移到 Next.js API Routes (Serverless Functions)

  │  │                                    ▼                              │   │
  │  │                    ┌─────────────────────────┐                   │   │
  │  │                    │   統一的 API 服務層     │                   │   │

**技術棧**：
- **資料庫**：Cloudflare D1 (SQLite 兼容，全球分發) 或 Turso
- **API**：Next.js API Routes (Serverless)
- **ADS-B**：透過 API Route 直接抓取樹莓派或 OpenSky
- **部署**：Vercel (自動)

**優點**：
| 優點 | 說明 |
|------|------|
| 單一部署單位 | 前後端都在 Vercel，無同步問題 |
| 全球低延遲 | Cloudflare D1 全球邊緣節點 |
| 自動擴展 | Serverless 自動應對流量 |
| 免費額度 | Vercel + Cloudflare D1 有 generous free tier |
| 維護簡單 | 一個 repository，一個部署流程 |

**缺點**：
| 缺點 | 說明 |
|------|------|
| 外部 API 依賴 | OpenSky/桃機官網 API 可能不穩定 | 需要穩定的網路連線 |
| Cold Start | Serverless 函數有冷啟動延遲 |
| 運算限制 | Serverless 有記憶體和執行時間限制 |
| ADS-B 私密 IP | 樹莓派在私有網路，Vercel 無法直接訪問 |

**適用場景**：新創專案、追求快速迭代、需要全球訪問的服務

**技術棧**：
- **後端框架**：FastAPI (Python) 替換現有的 api_server.py
- **API 閘道**：Next.js API Routes 作為代理
- **部署**：i5 伺服器 + Vercel 前端
- **網址暴露**：使用 ngrok、Cloudflare Tunnel 或固定域名

**優點**：
| 優點 | 說明 |
|------|------|

| 缺點 | 說明 |

| 部署複雜 | 兩套系統需要分別部署和監控 |
| 擴展性有限 | 伺服器頻寬和效能有物理限制 |

**適用場景**：已有穩定 Python 後端，不希望完全重寫的專案

### 2.3 方案 C：維持現狀 + 最小修復

**技術棧**：
- **幾乎不變**：維持現有架構
- **新增**：4 個 API Route 檔案
- **修改**：前端頁面 fetch 邏輯

**優點**：
| 優點 | 說明 |
|------|------|
| 改動最小 | 只需新增/修改少數檔案 |
| 風險最低 | 不動現有 Python 後端邏輯 |
| 快速見效 | 可能在一天內完成 |
| 熟悉度高 | 團隊對現有架構已有經驗 |

**缺點**：
| 缺點 | 說明 |
|------|------|
| 架構問題未解決 | 根本設計缺陷依然存在 |
| 同步延遲 | 依賴 pull_from_server.py 的執行頻率 |
| 維護複雜 | 兩套系統仍需分別維護 |
| 擴展性差 | 遲早會遇到效能瓶頸 |
| 錯誤回審機制弱 | 沒有統一的資料驗證層 |

**適用場景**：臨時修復、資源有限、不想破壞現有流程的團隊

## 3. 方案 A / B / C 優缺點總表

| 維度 | 方案 A (全雲端) | 方案 B (混合 API) | 方案 C (最小修復) |
|------|----------------|------------------|------------------|
| **開發時間** | 2-4 週 | 1-2 週 | 1-2 天 |
| **改動範圍** | 全量重寫 | 重構 API 層 | 新增 API Routes |
| **部署複雜度** | 簡單 (單一流程) | 中等 (雙部署) | 簡單 |
| **即時性** | 中等 (依外部 API) | 最佳 (直接查 DB) | 差 (同步延遲) |
| **維護成本** | 低 | 中 | 中 |
| **擴展性** | 極佳 | 有限 | 差 |
| **Serverless 冷啟動** | 有 | 無 | 無 |
| **外部 API 穩定性** | 需處理 | 需處理 | 需處理 |
| **資料一致性** | 最佳 | 最佳 | 差 |
| **錯誤回審機制** | 可統一建制 | 可統一建制 | 各自為政 |
| **公有雲費用** | Vercel free tier 足夠 | Vercel + 伺服器電費 | 幾乎無額外費用 |
| **風險** | 低 (新系統) | 中 (API 重構) | 低 (小改動) |
| **長期可維護性** | 最佳 | 良好 | 差 |

                    │
                    │

### 4.2 推薦選擇

| 你的情況 | 推薦方案 |
|----------|----------|
| 有時間和資源重構 | **方案 A** - 全雲端 Serverless |
| 希望保留 Python 後端但改善架構 | **方案 B** - 混合 API |
| 臨時修復、資源有限 | **方案 C** - 最小修復 |

### 4.3 我的建議

**如果要我選，我會推薦方案 B（混合架構）**：

理由：
1. 你的 Python 後端邏輯已經非常成熟（bridge_v4.py 的 ADS-B 融合等了 3 個月優化）
2. 完全重寫成 Serverless 需要大量時間測試外部 API 穩定性
3. 混合架構可以在 1-2 週內見效，同時為未來遷移到全雲端做準備
4. i5 伺服器已經有固定 IP，可以透過 Cloudflare Tunnel 暴露到互聯網
